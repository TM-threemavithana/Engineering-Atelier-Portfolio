## Engineering Challenge & Context

Autonomous AI agents integrating LLM tool calling with relational databases introduce unprecedented security failure modes. When agents generate raw or parameterized SQL dynamically, conventional perimeter firewalls and application-layer ORMs are insufficient:

1. **Prompt Injection & Obfuscation:** Attackers can trick LLMs into embedding SQL injection payloads, stacked statements, or destructive DDL commands that bypass regex-based keyword filters.
2. **Side-Channel & Denial of Service:** Malicious or hallucinated agent queries can invoke `EXPLAIN ANALYZE` (executing arbitrary queries under the guise of inspection) or manipulate `statement_timeout` to cause resource exhaustion.
3. **Cross-Tenant Data Exposure:** Shared agent tool instances often access multi-tenant databases without reliable, compile-time row-level isolation guarantees.
4. **Connection Exhaustion:** Agents holding open database connections during multi-second LLM inference loops rapidly saturate physical database connection limits.

AgentIAM was engineered as an inline, wire-protocol database proxy in Go that treats all AI-generated SQL queries as untrusted, inspecting and enforcing security policies before execution.

## System Architecture & Interception Pipeline

AgentIAM sits directly on the TCP network path between AI agents and target databases, implementing both the PostgreSQL wire protocol (`pgproto3`) and the MySQL client/server protocol (`go-mysql-org/go-mysql`).

```
[ AI Agent / LLM Tool ]
        │ (PostgreSQL / MySQL Wire Protocol)
        ▼
┌────────────────────────────────────────────────────────┐
│ AgentIAM Security Proxy (Go)                           │
│                                                        │
│  1. Wire Interception (TLS / mTLS / SCRAM-SHA-256)     │
│  2. SQL AST Parser (wasilibs/go-pgquery & PingCAP)     │
│  3. Policy Engine (Statement Whitelist, Max Complexity)│
│  4. Tenant Isolation Rewriter (Subquery Injection)     │
│  5. M:N Transaction Multiplexer (pool.go)              │
└────────────────────────────────────────────────────────┘
        │ (Physical Pooled Connection + DISCARD ALL)
        ▼
[ Upstream Database (PostgreSQL 16 / MySQL 8.0) ]
```

### Request Lifecycle

1. **Wire Interception & Handshake:** The agent connects using standard database drivers (`pgx`, `psycopg`, `mysqlclient`). AgentIAM negotiates TLS/mTLS and verifies credentials via SCRAM-SHA-256.
2. **AST Parsing:** Queries are compiled into an Abstract Syntax Tree using WebAssembly-compiled PostgreSQL 16 engine code (`wasilibs/go-pgquery`) or PingCAP's TiDB MySQL parser.
3. **Recursive Policy Validation:** The AST is traversed to enforce strict statement allowlists (`SELECT`, `INSERT`, `UPDATE`, `DELETE`), rejecting unapproved DDL or administrative commands.
4. **Tenant Isolation Rewriting:** If tenant isolation is enabled, table references are transformed into isolated subqueries before dispatch.
5. **Upstream Execution & Pool Release:** The rewritten query executes on a pooled upstream connection. Upon receiving `ReadyForQuery`, the upstream connection is scrubbed via `DISCARD ALL` and returned to the pool.

## Key Engineering Decisions & Trade-offs

### 1. Wire-Protocol Proxy vs. Client SDK Library

- **Decision:** Intercept database wire protocols at the binary stream level rather than relying solely on a client-side SDK.
- **Trade-off:** Implementing wire state machines (`pgproto3`) requires deep protocol fidelity, but guarantees language-agnostic enforcement that cannot be bypassed by misconfigured agent tool code.

### 2. C/Wasm AST Parsing vs. Regex Guardrails

- **Decision:** Compile full syntax trees via WebAssembly (`wasilibs/go-pgquery`) instead of using regular expressions or secondary LLM evaluators.
- **Trade-off:** AST parsing incurs computational overhead per query compared to simple regex pattern matching, but reliably parses grammar structure and prevents syntactic bypasses such as comment obfuscation, nested subqueries, and stacked multi-statement injection.

### 3. M:N Connection Multiplexing with State Sanitization

- **Decision:** Multiplex client agent connections over a compact pool of physical database connections, releasing the upstream connection when the transaction state returns to idle.
- **Hygiene Requirement:** Because PostgreSQL connections retain session variables, temporary tables, and prepared statements, AgentIAM automatically issues `DISCARD ALL` upon connection release, preventing cross-tenant session leakage.

## Implementation Details & Security Hardening

- **`EXPLAIN ANALYZE` Prevention:** In PostgreSQL, `EXPLAIN ANALYZE` actually executes the query to collect timing statistics. AgentIAM inspects `ExplainStmt.Analyze` in the AST and immediately rejects it, preventing side-channel execution attacks.
- **Timeout Bypass Protection:** Fixed in commit `5b7e7fcd`, AgentIAM blocks both `SET statement_timeout` and function calls like `SELECT set_config('statement_timeout', ...)` to prevent rogue agents from disabling query deadlines.
- **Smart Parameter Caching:** Parsed AST templates are cached using an LRU cache (`hashicorp/golang-lru/v2`). Statements containing raw string literals bypass the cache to prevent cache exhaustion.

## Verification & Limitations

### Automated Test Coverage

The AgentIAM repository test suites include:

- **Unit Tests:** 48 AST firewall tests, 32 tenant isolation rewrite tests, and 26 MySQL parser test cases verified in source.
- **CI Execution:** GitHub Actions (`ci.yml`) runs unit and benchmark suites against an ephemeral `postgres:16` container.
- **Concurrency & State Tests:** High-concurrency connection pool tests validating `DISCARD ALL` execution and connection recycling under load.

### Transparent Engineering Limitations

- **View Masking Bypass:** Data masking operates strictly on static AST table mappings (`rules.MaskedColumns`). Because the proxy does not replicate database schema catalogs (`pg_class`), it cannot trace an unrestricted view back to a masked base table. If a view wraps a masked table, queries against the view bypass data masking unless database administrators enforce strict database-level `GRANT / REVOKE` restrictions.
- **Open Upstream Advisory (GO-2026-4518):** In `github.com/jackc/pgproto3/v2@v2.3.3`, a negative column length in an upstream `DataRow` packet triggers a panic during decoding. In the absence of an upstream v2 patch, background receive loops require defensive panic containment, and deployments should enforce strict upstream TLS validation.
- **Warehouse Dialects:** Snowflake and BigQuery parsers use regex preprocessing before ANSI parsing, which can encounter edge cases on complex vendor-specific SQL extensions. These adapters remain experimental.
- **Performance Framing:** Unsupported high-concurrency numbers and connection-overhead claims are omitted from this case study in favor of verifiable qualitative architectural guarantees.
