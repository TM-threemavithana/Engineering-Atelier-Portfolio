## 1. Project Overview & The Platform Engineering Challenge

Modern enterprise backend development demands more than writing functional REST endpoints. High-assurance systems require strict transactional integrity, non-blocking concurrent writes, and owner-scoped data access at the application tier—coupled with automated delivery, continuous observability, and verified disaster recovery at the platform tier.

However, organizations frequently suffer from two operational extremes:

1. **The Cloud Black-Box Trap:** Cloud hyperscalers (AWS, GCP, Azure) provide convenient managed services, but abstract away fundamental infrastructure mechanics—such as container network routing, storage volume persistence, Linux cgroups, and TLS termination—while imposing steep recurring compute and data egress fees that discourage aggressive chaos injection and recovery rehearsals.
2. **The Eventual Consistency Fallacy:** Many distributed architectures default to complex asynchronous messaging and eventual consistency for workflows that fundamentally demand strict ACID guarantees, leading to subtle race conditions, lost updates, and corrupted relational state.

**ForgeTasks & ForgeOps** resolves this duality through an intentional two-tier architecture:

- **ForgeTasks API (Application Layer):** A modern Java 21 LTS / Spring Boot 4.1.2 RESTful service built with Jakarta Persistence (JPA), Hibernate 6, Flyway migrations, and PostgreSQL 16. It enforces version-based HTTP optimistic concurrency control via ETags, BCrypt-authenticated owner-scoped relational data isolation, and RFC 7807/9457 `ProblemDetail` error contracts.
- **ForgeOps Platform (Infrastructure & SRE Layer):** A self-hosted, reproducible GitOps delivery and observability platform running on a local-first Kubernetes (Kind) cluster. It integrates pull-based continuous delivery via Argo CD, dual-escrow secret encryption via Mozilla SOPS and `age`, client-side policy-as-code with Kyverno, and three-pillar correlated telemetry powered by Grafana Alloy, Loki, Tempo, and Prometheus.

Every metric, latency percentile, and recovery time objective documented in this case study is derived from actual captured command execution logs within the repository's 15-gate verification suite.

## 2. Why the System Was Built

Production systems frequently fail not because business logic is incorrect, but because the underlying platform and concurrency boundaries were never subjected to real failure conditions:

- **Lost-Update Anomalies:** In collaborative task systems, two users concurrently modifying the same record will overwrite each other's changes if the API relies on uncoordinated `PUT` or `PATCH` updates. Standard database pessimistic locks (`SELECT ... FOR UPDATE`) solve this at the expense of database thread contention, connection pool starvation, and distributed deadlocks.
- **Hidden Deployment Failures:** Traditional push-based CI/CD pipelines use imperative scripts (`kubectl apply` or `helm install`) that bypass version control as the single source of truth, mask partial rollouts, and lack automated rollback safeguards when faulty container images are pushed.
- **Fragmented Observability Silos:** When an API request experiences elevated latency or returns HTTP 500, engineers often waste hours correlating disparate systems: searching disconnected log aggregators, inspecting disconnected metric dashboards, and tracing unlinked network spans.
- **Theoretical Disaster Recovery:** Most disaster recovery plans exist solely on paper. Without automated, non-destructive restoration drills executed against disposable validation targets, organizations have no verified evidence of their actual Recovery Time Objective (RTO) or Recovery Point Objective (RPO).

ForgeTasks and ForgeOps was engineered from first principles to solve these challenges in an auditable, zero-cost, local-first lab environment that mirrors enterprise platform standards.

## 4. Architectural Requirements & System Invariants

To guarantee production-grade safety without enterprise cloud overhead, ForgeTasks and ForgeOps enforce five non-negotiable architectural invariants:

### 1. Version-Based HTTP Optimistic Concurrency Control (ADR-0013)

To prevent lost updates in multi-client environments, mutating endpoints (`PATCH /api/v1/tasks/{id}` and `DELETE /api/v1/tasks/{id}`) enforce version-based optimistic concurrency control:

- Every resource response contains an `ETag` header formatted with quoted version values (e.g. `ETag: "3"`), derived directly from the JPA `@Version` column (`version = 0L`).
- Clients mutating or deleting a task must supply the `If-Match` request header.
- If `If-Match` is omitted, `TaskService` halts immediately by throwing `PreconditionRequiredException`, mapped by the global exception handler to **HTTP 428 Precondition Required** (`application/problem+json`).
- If `If-Match` does not match the current database entity version, the service throws `PreconditionFailedException`, returning **HTTP 412 Precondition Failed** with RFC 7807/9457 problem details.
- ETag parsing and formatting is handled via `ETagUtils`: `parseIfMatch` strips surrounding quotes and accepts weak prefixes (`W/"..."`), parsing the underlying numeric version rather than performing full RFC 7232/9110 byte-for-byte strong comparison validation.
- This mechanism eliminates database row deadlocks while providing non-blocking reads and deterministic concurrency protection.

### 2. Owner-Scoped Relational Data Isolation & Assignment Boundaries

ForgeTasks enforces ownership boundaries directly in the relational domain model:

- **Owner-Scoped Queries:** Tasks belong to Projects, and Projects belong to Accounts. Mutating and retrieval queries join against the authenticated account: `taskRepository.findByIdAndOwner(taskId, owner)` and `projectRepository.findByIdAndOwner(projectId, owner)`.
- **Enumeration Defense:** When an authenticated caller requests a task or project owned by another account, the repository query returns empty. `TaskService` throws `ResourceNotFoundException`, resulting in **HTTP 404 Not Found** rather than HTTP 403 Forbidden, mitigating resource enumeration across accounts.
- **Assignment Scope Boundary:** While project ownership and task mutations are strictly owner-scoped, assigning a task (`assignedAccountId` in `createTask` and `updateTask`) verifies account existence via `accountRepository.findById(id)`. Because the prototype does not define an organizational boundary or tenant group model, task assignment can reference any existing registered account in the system rather than being restricted to an organizational boundary.

### 3. Pull-Based GitOps with Push-to-Pull Inversion (ADR-0004)

Direct deployment from developer workstations or CI runners (`kubectl apply`) is strictly prohibited:

- GitHub Actions CI builds immutable container images tagged with git commit SHAs, signs them, and publishes them to GitHub Container Registry (GHCR).
- Argo CD continuously monitors the repository and synchronizes cluster state to match Git.
- In production rehearsal environments (`G08`), automated sync was intentionally disabled (`syncPolicy.automated.enabled: false`) to require human review before applying changes, preventing automated failure cascades during recovery drills.

### 4. Client-Side Policy Enforcement Shift-Left (ADR-0010)

Dynamic Kubernetes admission webhooks inside a single-node local cluster introduce severe failure modes: if an in-cluster validating webhook pod runs out of memory or crashes, the Kubernetes API server blocks all pod scheduling and bricks the cluster.

ForgeOps shifts policy evaluation left: **Kyverno CLI (`kyverno apply`) runs client-side in GitHub Actions CI**. It audits 100% of Helm-rendered manifests against 10 security policies (disallowing root UIDs, privilege escalation, host namespaces, and writable root filesystems) before pull requests can merge.

### 5. Clean-Room Target Isolation for Disaster Recovery (ADR-0008)

Automated database restoration drills must never target an active operational database. Early DR automation that executed `pg_restore --clean` risked irreversible data loss if executed against the wrong namespace.

ForgeOps mandates that disaster recovery rehearsals execute strictly against a **disposable target namespace (`forgeops-dr-lab`)**. Restores are performed into freshly initialized databases with `--exit-on-error`, asserting zero pre-existing application tables and verifying complete relational and BCrypt authentication integrity before teardown.

## 6. Implementation Deep-Dive: Concurrency, Correlation, and Schema Lifecycle

The ForgeTasks backend couples Spring Boot 4 web MVC with declarative transaction management and strict request tracing.

### 1. HTTP ETag Optimistic Concurrency Validation

When a task update is submitted via `PATCH /api/v1/tasks/{id}`, the controller extracts the `If-Match` header and passes the parsed version to `TaskService`:

```java
// TaskService.java: Optimistic Concurrency Check & Precondition Enforcement
@Transactional
public TaskResponse updateTask(UUID taskId, String username, TaskUpdateRequest request, Long ifMatchVersion) {
    Account owner = getAuthenticatedAccount(username);
    Task task = taskRepository.findByIdAndOwner(taskId, owner)
            .orElseThrow(() -> new ResourceNotFoundException("Task not found with id: " + taskId));

    if (ifMatchVersion == null) {
        throw new PreconditionRequiredException("Header 'If-Match' is required for mutating task updates.");
    }

    if (!task.getVersion().equals(ifMatchVersion)) {
        throw new PreconditionFailedException("Supplied If-Match version " + ifMatchVersion +
                " does not match current resource version " + task.getVersion() + ".");
    }

    if (request.title() != null && !request.title().isBlank()) {
        task.setTitle(request.title());
    }
    if (request.description() != null) {
        task.setDescription(request.description());
    }
    if (request.status() != null) {
        task.setStatus(request.status());
    }
    if (request.priority() != null) {
        task.setPriority(request.priority());
    }
    if (request.dueDate() != null) {
        task.setDueDate(request.dueDate());
    }
    if (request.assignedAccountId() != null) {
        Account assigned = accountRepository.findById(request.assignedAccountId())
                .orElseThrow(() -> new ResourceNotFoundException("Assigned account not found with id: " + request.assignedAccountId()));
        task.setAssignedAccount(assigned);
    }

    Task updated = taskRepository.saveAndFlush(task);
    return TaskResponse.from(updated);
}
```

The corresponding web controller wraps the returned entity and formats the updated version into an HTTP `ETag` header:

```java
// TaskController.java: ETag Formatting and Header Parsing
@PatchMapping("/tasks/{id}")
public ResponseEntity<TaskResponse> updateTask(
        @PathVariable UUID id,
        @RequestHeader(value = HttpHeaders.IF_MATCH, required = false) String ifMatch,
        @Valid @RequestBody TaskUpdateRequest request) {

    String username = getCurrentUsername();
    Long version = ETagUtils.parseIfMatch(ifMatch);
    TaskResponse response = taskService.updateTask(id, username, request, version);

    return ResponseEntity.ok()
            .eTag(ETagUtils.formatETag(response.version()))
            .body(response);
}
```

### 2. Request Correlation & Distributed Context Propagation

To guarantee that incoming HTTP requests can be traced across log streams and Tempo spans, the `RequestCorrelationFilter` executes at the highest precedence filter boundary:

```java
// RequestCorrelationFilter.java: X-Request-ID Extraction and MDC Binding
@Component
@Order(Ordered.HIGHEST_PRECEDENCE)
public class RequestCorrelationFilter extends OncePerRequestFilter {

    public static final String CORRELATION_ID_HEADER = "X-Request-ID";
    public static final String MDC_CORRELATION_KEY = "correlationId";
    private static final Pattern SAFE_CORRELATION_ID_PATTERN = Pattern.compile("^[a-zA-Z0-9\\-_]{8,64}$");

    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response, FilterChain filterChain)
            throws ServletException, IOException {

        String correlationId = request.getHeader(CORRELATION_ID_HEADER);
        if (correlationId == null || !SAFE_CORRELATION_ID_PATTERN.matcher(correlationId.trim()).matches()) {
            correlationId = UUID.randomUUID().toString();
        } else {
            correlationId = correlationId.trim();
        }

        MDC.put(MDC_CORRELATION_KEY, correlationId);
        response.setHeader(CORRELATION_ID_HEADER, correlationId);

        try {
            filterChain.doFilter(request, response);
        } finally {
            MDC.remove(MDC_CORRELATION_KEY);
        }
    }
}
```

2. **Readiness Probe Failure Injection:** A synthetic failure was injected into a replica's readiness probe. The unhealthy pod was immediately excluded from service endpoints; the probe recovered to healthy status in **706 milliseconds**.
3. **Invalid Image Rollout Guard:** A nonexistent container image tag was deployed via Helm. The deployment halted in `ErrImagePull` while existing healthy replicas continued serving traffic without downtime. The deployment was rolled back in **813 milliseconds**.
4. **Bounded Resource Pressure:** Handled 1,052 requests up to the 20 req/s ceiling with zero process memory bloat and zero container restarts.
5. **Declarative Drift Reconciliation:** An imperative scaling modification (`kubectl scale --replicas=5`) was executed against the cluster. Argo CD detected the out-of-sync drift and reconciled the deployment back to the desired Git state (2 replicas) in **1.47 seconds**.

## 8. PostgreSQL Disaster Recovery & Rehearsal Verification (Gate G13)

Disaster recovery readiness was verified through an automated rehearsal script (`scripts/cluster/dr/rehearse-dr.sh`) performing non-destructive recovery into an isolated disposable test target.

### The Clean-Room Disposable Target Pattern

To eliminate blast-radius risk against operational databases while preserving the live cluster baseline, the rehearsal drill executed against an ephemeral target in `forgeops-dr-lab` without destroying the active Kind cluster:

1. **Synthetic State Generation:** Seeded a synthetic relational dataset: 2 accounts (`dr_admin`, `dr_user` with real BCrypt hashes), 2 projects, and 4 tasks with versioning.
2. **Compressed Logical Backup:** Executed `pg_dump -Fc` via local port-forward in **273 milliseconds**, generating a 10,675-byte custom-format archive.
3. **Cryptographic Manifest Verification:** Computed the SHA-256 hash (`132646cba1ea1b2bb5a7d377bf188cf4c8038b1f558ef2333066373b5dfd46ff`) and verified binary magic headers (`PGDMP`) and Table of Contents (TOC) entries.
4. **Target Freshness Guard:** The restore script asserted that the destination database contained zero application tables before proceeding, rejecting any attempt to restore over existing data.
5. **Strict Clean-Room Restoration:** Executed `pg_restore --exit-on-error` into the disposable target database in **252 milliseconds**.
6. **End-to-End Service Validation:** Deployed a fresh ForgeTasks API instance pointing to the restored database. Executed authentication smoke tests, verifying that BCrypt credentials, relational foreign keys, and task entities were fully accessible.

### Quantitative Disaster Recovery Metrics:

- **Logical Backup Execution Time (`pg_dump -Fc`):** **273 ms** (10,675-byte custom-format archive).
- **Database Restoration Execution Time (`pg_restore`):** **252 ms** (schema and row loading into disposable target).
- **End-to-End Service Recovery RTO:** **89.29 seconds** (total elapsed rehearsal time: disposable database provisioning, schema restoration, Spring Boot pod startup, readiness probe stabilization, and authenticated REST smoke testing).
- **Measured Backup Age (Currency):** **12.00 seconds** (the age of the test snapshot when restored during the rehearsal drill).
- **Protected PVC Continuity:** Throughout the drill, all **5 protected baseline PersistentVolumeClaims remained 100% intact with zero UID mutation or storage leaks**.

> [!NOTE]
> **Disaster Recovery Scope & Simulation Boundaries:** The drill demonstrated automated non-destructive schema and data restoration into an isolated disposable target (`forgeops-dr-lab`) with cryptographic SHA-256 verification. The live operational cluster, nodes, and persistent volumes were not destroyed during this exercise. The procedure utilizes discrete, point-in-time logical backups (`pg_dump -Fc`); it does not demonstrate multi-node physical cluster recovery, continuous streaming Write-Ahead Log (WAL) archiving with point-in-time recovery (PITR) to cloud object storage, or recovery from total hardware host loss.

## 9. Platform Security, Secret Hygiene & Policy-as-Code (Gate G14)

Platform security in ForgeOps implements a defense-in-depth posture spanning secrets management, container runtime constraints, and CI policy enforcement.

### Asymmetric Secret Encryption with Dual Escrow (ADR-0011)

Kubernetes secrets committed to Git are encrypted using Mozilla SOPS with `age` public-key cryptography:

- Secrets are encrypted for two distinct asymmetric recipients: `Primary Operational` and `Recovery Escrow`.
- Configuration uses value-only encryption (`encrypted_regex: '^(data|stringData)$'`). Kubernetes metadata, secret names, labels, and annotations remain unencrypted in plaintext, enabling linters, Kustomize, and Git diff tools to inspect resources without decrypting sensitive payloads.
- Zero private keys or plaintext secrets exist in git history.

### Client-Side Kyverno Policy Enforcement (ADR-0010)

Ten Kyverno policies enforce Kubernetes Restricted Pod Security Standards and hygiene across all Helm-rendered manifests:

1. `disallow-privileged-containers`: Disallows `privileged: true` in container security contexts.
2. `disallow-privilege-escalation`: Mandates `allowPrivilegeEscalation: false`.
3. `require-run-as-non-root`: Enforces `runAsNonRoot: true` (UID `10001`).
4. `require-drop-all-capabilities`: Requires explicit `drop: ["ALL"]` on all containers.
5. `require-seccomp-default`: Mandates `seccompProfile.type: RuntimeDefault` or `Localhost`.
6. `disallow-latest-tag`: Rejects `:latest` tags and untagged image references.
7. `require-resource-requests-limits`: Mandates explicit CPU and memory requests and limits.
8. `disallow-host-namespaces`: Prevents pods from sharing host PID, IPC, or network namespaces.
9. `restrict-image-registries`: Restricts images to approved registries (pattern-matched hostname enforcement).
10. `require-security-labels`: Mandates standard `app.kubernetes.io/name` and security tier metadata labels.

In Gate G14 verification, the Kyverno CLI executed client-side in GitHub Actions CI across 20 positive and negative test cases, recording a **20/20 (100%) pass rate** before code merge. Running policy validation client-side in CI explicitly eliminated in-cluster admission webhook memory overhead and prevented cluster deadlock failure modes on local developer workstations.

## 10. Engineering Lessons, Postmortems & Architectural Boundaries

### Operational Postmortems & Key Lessons:

- **The OCI Attestation vs. Runnable Image Digest Incident (Gate G10):** When automating image promotion from GitHub Container Registry (GHCR), an automated release script mistakenly captured an OCI attestation manifest digest (SLSA provenance JSON) instead of the runnable Linux container image. The container runtime failed with `executable file not found in $PATH`. The incident was contained without downtime because Kubernetes rolling updates held the healthy replica. We resolved this by introducing a pre-flight verification script (`test_publish_hardening.py`) that strictly validates container image MIME types (`application/vnd.docker.distribution.manifest.v2+json`) before updating Helm values.
- **TCP Socket Exhaustion Under High Load (Gate G12):** Early k6 load testing over `kubectl port-forward` caused intermittent connection timeouts due to local host TCP socket exhaustion over single SPDY multiplexed streams. Adding arrival-rate throttling (20 req/s, 25 VUs) eliminated socket exhaustion, achieving 2,275 requests with 0.00% errors and sub-7 ms p95 latencies.
- **The Danger of `pg_restore --clean` in Disaster Recovery (Gate G13):** Initial DR scripts used `pg_restore --clean`, which issues `DROP TABLE` before recreating objects. When chained with non-fatal shell commands, a corrupted archive could drop active tables and leave the system empty. We replaced this with the disposable target pattern: restores are performed exclusively into fresh, empty databases with `--exit-on-error` and strict exit code trapping.

### Known Architectural Boundaries:

- **Single-Node Kind Limitations:** The cluster operates on a single Docker container host inside WSL2. Physical node hardware failures, split-brain cross-hypervisor network partitions, and WAN latency are not modeled.
- **NetworkPolicy Scope:** Default `kindnet` implements basic IPAM and NAT routing, but does not enforce Kubernetes `NetworkPolicy` packet filtering at the kernel layer. Enforcing kernel-level egress/ingress dropping requires deploying an eBPF CNI such as Cilium.
- **Local Secret Custody:** `age` private keys reside on the operator's local filesystem rather than a dedicated cloud Key Management Service (AWS KMS, GCP KMS) or Hardware Security Module (HSM).
- **Manual Argo CD Synchronization:** Automatic synchronization is intentionally disabled in rehearsal environments to prevent automated reconciliation loops during fault drills, requiring operator review before applying changes.
